## 1. 为什么切 3 批

M2 共 21 个功能点（F-D5~D13 九项 + F-E6~E17 十二项），体量超过 M1 的 40 点里的相当一部分。
SPEC-00 §3 的分批原则是「**每批结束都能独立跑出一条用户能用的链路**，不留下半截功能」。

单批 21 点会同时踩两个坑：
- 中途无法独立验收，坏了不知道坏在哪一环
- 前端 5 个占位页（`hot` / `topics` / `calendar` / `analytics` / `accounts`）背后全无
  `api/` 路由，一次性铺开 review 面太大

切分依据是**用户链路**，不是按功能类型分组——每批结束都能自己走通一遍。

## 2. 三子批

### M2-1 · 选题（把「写什么」从拍脑袋变成有据可依）

| 项 | 内容 |
|---|---|
| 功能点 | F-E8 爆款拆解（P0）· F-E9 选题评分 · F-E10 内容矩阵 · F-E11 标题 Hook |
| 后端 | `atelier/server/topics/{service,decode,score,matrix}.py` + `api/topics.py` |
| 前端 | `web/src/features/topics/`（`topics` 占位页转正） |
| 新表 | `topics` / `topic_scores`（schema v3） |

**为什么排第一**：F-E8 是 M2 唯一的 P0，且它**不依赖任何外部数据源**——
用户粘贴一段对标内容就能拆，是纯 AI 能力。风险最低、价值最直接，适合先跑通。

出口标准：
1. 粘贴对标内容 → 出 6 段式拆解（概括/钩子/结构/为何火/可复制模板/结合画像出选题）
2. 选题按 7 维打分，给出「做/不做/改方向」的明确结论，不是只给分
3. 内容矩阵（支柱 × 格式）能一键生成选题池
4. 标题 Hook 出多变体，且**每个变体都过字数校验**（复用 M1 的 `gates/wordcount.py`）

> 复用提醒：M1 集成时踩过「门禁与预检两套字数口径」的坑（ACCEPTANCE-M1 §5 bug #1）。
> M2-1 的 Hook 字数校验**必须**经 `gates/wordcount.py` 转发复用，不得另写一套计数。

---

### M2-2 · 日历与热点（把「今天发什么」从手动变成有数据）

| 项 | 内容 |
|---|---|
| 功能点 | F-D8 热点日报（P2）· F-D9 事件日历 · F-E6 平台活动日历 · F-E7 日历建议（P2） |
| 后端 | `atelier/server/calendar/{service,suggest}.py` + `api/calendar.py` |
| 前端 | `web/src/features/calendar/`（占位页转正） |
| 新表 | `calendar_events` / `hot_digests` |

**为什么排第二**：依赖 M2-1 的选题池（日历建议要能往选题池里塞东西），
且是三个批次里**唯一依赖外部数据**的。数据源可靠性是最大风险，放到有 M2-1 打底之后做，
出问题时不至于让整个 M2 卡住。

出口标准：
1. 节日/电商节点/行业事件入日历，提前 N 天提醒
2. 热点日报是结构化摘要，不是原始链接堆砌
3. 日历建议能直接生成近 14 天选题并落进 M2-1 的选题池

> **诚实前置**：热点抓取依赖平台数据可得性。抖音/小红书均无公开热点 API，
> 抓取方案在开工前需单独评估（RSS / 第三方聚合 / 手工导入），
> **不要在计划阶段假装它一定能自动抓到**。

### M2-3 · 发现与分析（长尾增强）

| 项 | 内容 |
|---|---|
| 功能点 | F-D5 博主订阅 · F-D6 深度加载 · F-D7 RSS 聚合 · F-D10 竞品分析 · F-D11 内容缺口 · F-D12 算法追踪（P3）· F-D13 UGC 发现（P3）· F-E12 内容策略 · F-E13 账号诊断 · F-E14 受众画像 · F-E15 营销策划（P3）· F-E16 直播策划（P3）· F-E17 商单（P3） |
| 后端 | `atelier/server/discovery/**` + `api/discovery.py`、`api/analytics.py` |
| 前端 | `web/src/features/`（`accounts` / `analytics` 占位页转正） |
| 新表 | `subscriptions` / `competitors` / `content_gaps` |

**为什么排最后**：13 个点里 5 个是 P3（算法追踪 / UGC / 营销策划 / 直播策划 / 商单），
且高度依赖 M2-2 建立的数据积累。**没有前两批攒下的真实选题与发布记录，
F-D11 内容缺口和 F-E13 账号诊断都算不出来**——硬做只能出假数据。

出口标准：
1. 订阅博主 → RSS 按关键词时间窗过滤去重
2. 竞品拆解出选题/格式/爆款规律
3. 内容缺口分析能指出「高需求低竞争」方向
4. 账号诊断基于**真实发布记录**，不是编出来的分数

> ⚠️ **不做假数据**：如果 M2 结束时真实发布记录仍为空（M4 才补真实发布），
> F-E13 账号诊断必须**明确显示「数据不足，发布 N 条后才有诊断」**，
> 而不是退化成一套看着能用的假分数。这是 M1 已在 `cover_ratio` 上踩过的同类坑
>（ACCEPTANCE-M1 §6：按文件名判定而非读图片二进制）。

## 3. 跨批次约束

沿用 M1 的做法，这几条是硬规则：

| 规则 | 说明 |
|---|---|
| **路径收口** | 唯一允许拼路径的地方是 `server/paths.py`（SPEC-00 §1 ③） |
| **门禁复用** | 字数/合规一律经 `gates/` 转发，不许各域各写一套 |
| **新能力走注册表** | 新技能加 `skills/<id>/SKILL.md`；新门禁注册进 `gates/registry.py`；**不改既有文件加能力** |
| **落库不静默** | 持久化失败要 `log.exception` 留痕并降级，不许默默吞（`skills/store.py` 是范本） |
| **前置先改 spec** | 要改 `paths.py` / `harness/base.py` / `gates/base.py` 公开签名，先改 spec |
| **产出先过门禁** | AI 落盘必须经 `atelier_artifact_write`，MCP tool 不可绕过 |

### 文件归属（并行时按此切，Wave 1 必须先冻结共享契约）

| 子批 | 拥有（可写） | 禁止触碰 |
|---|---|---|
| **M2-1 选题** | `atelier/server/topics/**`、`api/topics.py`、`web/src/features/topics/**` | 其余全部 |
| **M2-2 日历/热点** | `atelier/server/calendar/**`、`api/calendar.py`、`web/src/features/calendar/**` | 其余全部 |
| **M2-3 发现/分析** | `atelier/server/discovery/**`、`api/{discovery,analytics}.py`、`web/src/features/{accounts,analytics}/**` | 其余全部 |

`api/` 走 `main.py` 的 `_autoload_routers()` 自动发现，新增域**不需要改 `main.py`**。

## 4. 与其它批次的关系

| 批次 | 依赖本轮 |
|---|---|
| M3 制作能力扩展 | 需要 M1 门禁框架（M3-1 视觉质检挂到 `ai_flavor` 同级）——**已就绪** |
| M4 平台扩展 | 需要 M1 平台抽象被 3 个平台验证过——**已就绪**；但 M2-3 的 F-D11/F-E13 依赖真实发布数据，**M4 之前拿不到** |
| M5 归因 | 需要真实发布记录——**M4 之后才谈得上** |

> 即：M2-3 的两项分析功能（内容缺口、账号诊断）在 M4 之前**只能做到「数据不足时诚实提示」**。
> 这是批次顺序的固有限制，不是实现偷懒——写在这里免得 M2-3 验收时误判。
