## 1. 产品概述

### 1.1 一句话定义

**Atelier 是一个面向社交媒体创作者的私有内容工作台：把热点发现、选题策划、内容制作、多平台发布、数据复盘串成一条闭环，让创作者带着自己的账号上下文工作，而不是每次从零开始。**

### 1.2 核心命题

传统 AI 工具的问题不是「不会写文案」，而是**不知道你是谁**。同一个模型给不同的人写出来的东西没有区别，因为每次对话都是失忆的。

Atelier 的解法是**账号画像驱动**：用户先建立一个六维画像（定位/风格/受众/平台/偏好红线/长期记忆），此后所有 AI 产出都基于这个上下文。配合「产物走文件系统」的归档机制，内容的上下文、过程和成品始终绑定在同一个项目里。

**一句话对比：**

| | 通用 AI 工具 | Atelier |
|---|---|---|
| 上下文 | 每次对话失忆 | 六维画像持续生效 |
| 产出 | 停在对话框里 | 落盘归档，可发布 |
| 平台 | 只给文字 | 直接发到 7 个平台 |
| 反馈 | 不知道效果 | 数据回流画像 |

### 1.3 产品边界（明确不做什么）

| 不做 | 原因 |
|---|---|
| 团队协作 / 多租户 SaaS | 定位是**个人私有工具**，单用户本地运行 |
| 移动端 App | Web 工作台已覆盖主要场景，移动端适配 P2 |
| 自建大模型训练 | 依赖成熟 LLM，不做训练 |
| 内容审核平台 | 只做发布前自检，不做合规仲裁 |
| 电商 / 直播带货闭环 | 策划层有营销方案能力，但不接交易链路 |
| 商业化 / 多租户 / 计费 | **本期定位为个人自用**，商业化路径留待后续决策（见 15.1） |

## 2. 目标用户

### 2.1 核心用户画像

**主用户：独立内容创作者 / 个人 IP 操盘手**

- 一个人或小团队运营 1–3 个社媒账号
- 已在某平台有基础，需要提升更新质量和稳定性
- 会用 ChatGPT/Claude，但产出「用完即弃」，没有沉淀
- 痛点：不知道发什么、写了记不住、发完不知道效果

**次用户：内容运营新人**

- 需要 SOP 化的创作流程，不完全懂平台规则
- 更依赖产品的引导和门禁，而不是自由发挥

### 2.2 用户核心场景

1. **今天发什么** —— 打开工作台看今日热点和待发排期
2. **从想法到成品** —— 对话里说清楚需求，产出可直接发布的图文/视频
3. **一份内容多平台发** —— 母版内容自动适配各平台格式
4. **账号越来越准** —— 发布数据回流画像，下一次产出更贴合

### 2.3 成功指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 首条成品产出时间 | 从安装到生成第一个可发布产物 | < 30 分钟 |
| 内容复用率 | 单份内容被改编到 ≥2 个平台的比例 | > 50% |
| 画像使用率 | 创建画像后实际启用的比例 | > 80% |
| 发布成功率 | 一次点击发布成功的比例 | > 70% |

## 3. 产品架构原则

这四条是从 Easel 实践中提炼的，**决定了很多功能的具体形态**，审核时请重点确认。

### 原则一：产物走文件系统，不走数据库

内容、素材、中间文件、元数据全部落在项目目录（`outputs/<项目名>/`），通过目录树浏览。

- **好处**：内容生产完全可审计、可回溯、可迁移，不依赖数据库备份
- **代价**：路径解析复杂，是历史技术债的主要来源
- **对新项目的建议**：保留文件系统为唯一真相源，但**把路径解析收口到一个模块**，不要散落在各处

### 原则二：AI 产出必须过确定性门禁

模型产出后，必须经过确定性脚本验收（字数校验、视觉质检、合规扫描），不过则重做。

- **好处**：把传统软件工程的 CI 纪律搬到 AI 产出上，比「相信模型」靠谱
- **代价**：增加流程复杂度
- **对新项目的建议**：门禁要分级——**硬门禁**（超字数、含密钥）阻断，**软提醒**（AI 味重、人设不符）只告警

### 原则三：付费操作必须显式确认

生图、生视频、生音乐等按量计费操作，先给费用预估，等用户确认再执行。

### 原则四：失败要留痕，不要静默

每轮对话落盘、长任务断线不中断、环境问题可诊断（doctor 检查）。**宁可丑，不要静默。**

## 4. 功能域 A：账号画像

> **这是整个产品的地基。** 画像没做好，其他功能都是无根之木。

### 4.1 功能清单

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F-A1 | 六维画像体系 | 定位 `identity` / 风格 `style` / 受众 `audience` / 平台 `platforms` / 偏好红线 `preferences` / 长期记忆 `memory` | **P0** |
| F-A2 | 画像创建向导 | 4 步引导：基础信息 → 社媒链接 → 运营意图 → 偏好红线 | **P0** |
| F-A3 | AI 辅助生成画像 | 从社媒链接分析已发内容，自动生成六维画像 | **P1** |
| F-A4 | 画像可视化编辑 | 六维分别编辑保存，Markdown 渲染 | **P0** |
| F-A5 | 多画像并行 | 多个画像共存，一键切换；同一画像可跨多平台 | **P0** |
| F-A6 | 长期记忆沉淀 | 归因结论自动沉淀；用户主动「记住这个偏好」 | **P0** |
| F-A7 | 平台数据自动写回 | 公众号等平台数据抓取后回写画像 | P2 |
| F-A8 | 画像导出/对比 | 导出画像文件、多个画像对比 | P3 |

### 4.2 关键设计

- **画像作为消息前缀内联**，不落全局文件。避免并发画像互相污染
- **每轮对话末尾重申「先查技能库」**，对抗长对话的指令衰减
- **无画像也能用**：提供「通用模式」，不强制引导

### 4.3 验收标准

- [ ] 用户可在无画像状态下完成任意创作任务（通用模式）
- [ ] 画像创建全程 < 3 分钟，可中途跳过
- [ ] 切换画像后，下一轮对话的产出风格可见变化
- [ ] 两个画像的对话不互相污染（并发验证）

## 14. 技术约束与架构决策

### 14.1 关键架构决策（需确认是否采用）

| 决策点 | 参考实现的做法 | 建议 |
|---|---|---|
| **AI 运行时** | 完全依赖 OpenClaw gateway | ⚠️ 抽象一层 harness 接口，避免深度绑定单一运行时 |
| **产物存储** | 文件系统 + 符号链接 | ✅ 采用，但路径解析收口到单一模块 |
| **编排代码组织** | 单文件 4933 行 | ❌ **不采用**，按能力域拆分模块 |
| **媒体 provider** | 可插拔注册表 | ✅ 采用，多家可切换是刚需 |
| **确定性优先** | 抠图/转写用本地模型 | ✅ 采用，省成本和隐私 |
| **出站内容闸门** | BLOCK/WARN 两级 | ✅ 采用，软硬分级的思路很对 |

### 14.2 已知的实践教训（应避免）

以下问题在参考实现中已被验证为技术债，**新项目应避免**：

1. **单文件后端膨胀** —— 4933 行单文件是最大技术债，发布/登录/数据三块约 1900 行
2. **运行时强耦合** —— 1500–2000 行用于适配特定运行时的 quirks（端口哈希、workspace 路径漂移、流式靠 tail 文件等）
3. **流式实现脆弱** —— 靠 tail 共享文件 + 闩锁捞取，不是标准推送
4. **传输层不可换边** —— 同一会话在两条路径间不能切换（会丢历史）
5. **文档漂移** —— 能力地图文档记录 113 个技能，实际 114 个
6. **安全边界模糊** —— Web API 无鉴权，虽已收紧 CORS 但仍不应暴露于公网
7. **平台风控不可控** —— 小红书等平台可能检测自动化，存在封号风险
